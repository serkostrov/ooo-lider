## 2. Цель Этапа 2

Довести систему до полного состава Приложения № 1 по блокам контроля, мобильной работы, экрана руководителя и выгрузок; выдать заказчику работающий стенд на его сервере и провести приёмку с обучением.

## 3. Что входит в Этап 2 (по блокам)

### Блок 7. Проверка и приёмка

**По договору:**
- исполнитель **не** закрывает этап сам;
- этап направляется на проверку и закрывается уполномоченным;
- на проверку — только при отмеченных условиях закрытия;
- возврат на доработку с причиной в карточке и в истории.

**Что сделать:**
- [ ] Прогнать и добить сценарий: «В работу → условия → На проверку → Принять / Вернуть».
- [ ] Проверить блокировку «На проверку» без отмеченных условий.
- [ ] Убедиться, что причина возврата видна в карточке и пишется в историю.
- [ ] Согласовать с заказчиком, кто именно «уполномоченный» на закрытие (роль / админ).

**Статус на старт планирования:** базовая логика в коде уже есть — нужна приёмка и доводка по замечаниям.

---

### Блок 8. Папка исполнительной документации (ИД)

**По договору:**
- автонакопление документов из условий закрытия с признаком «в папку ИД»;
- перечень недостающих: этап, исполнитель, дата отправки, срок ожидания;
- контроль комплектности перед герметичностью / опрессовкой;
- предупреждение при попытке закрыть такие этапы с неполной папкой.

**Что сделать:**
- [ ] Экран / вкладка **«Папка ИД»** на объекте (свод по всем этапам).
- [ ] Список собранных и недостающих позиций.
- [ ] Правила «критических» этапов (герметичность, опрессовка) — настройка или привязка к шаблонам.
- [ ] Блокировка / предупреждение при закрытии / приёмке при неполной папке.
- [ ] Связь с уже существующим флагом `to_id_folder` у условий и документов.

**Статус:** флаг «в папку ИД» есть; сводного экрана и автоконтроля нет — **ключевая новая работа**.

---

### Блок 9. Уведомления

**По договору:**
- персональные уведомления: напоминание по сроку, просрочка, нет ответа по документу, этап на проверке, нет исполнителя;
- переход из уведомления в карточку этапа;
- **дублирование в Telegram и email**.

**Что сделать:**
- [ ] Модель уведомлений в БД + лента / колокольчик в UI (если ещё не хватает сценариев).
- [ ] Фоновые проверки / триггеры по событиям сроков и статусов.
- [ ] Каналы: Telegram (бот + привязка пользователя), email (SMTP / провайдер заказчика).
- [ ] Настройки: куда слать, опционально отключение каналов.
- [ ] Deep-link / переход в карточку этапа.

**Статус:** просрочка и часть UI есть; Telegram / email и полноценная матрица событий — **сделать**.

### Блок 10. Мобильные рабочие места  
*(роли и доступы — уже Этап 1)*

**По договору (мобильная часть):**

- отметка условий закрытия;
- сообщение о **нештатной ситуации** с выделением объекта для всех;
- добавление работы вне регламента.

**Что сделать:**

- [ ] Экран «текущий этап» + крупные действия.
- [ ] Нештатная ситуация: флаг на объекте, видимость всем участникам / ролям.
- [ ] Добавление внерегламентной работы (по согласованной модели с заказчиком).
- [ ] Проверка на реальном телефоне / узкой ширине.

**Роли из Прил. № 1** (бригадир, геодезист, специалист по договорам): в ТЗ зафиксировано — на созвоне заказчик назвал другой набор; роли — справочник. В Этапе 2 не блокируем мобилку ожиданием этих ролей; при необходимости добавляем коды в справочник без переделки ядра.

### Блок 11. Экран руководителя

**По договору:**
- показатели по объекту: закрытые, просроченные, без ответа, ожидающие приёмки, без исполнителя;

- готовность по видам работ;
- **нагрузка по сотрудникам**.

**Что сделать:**

- [ ] Массовые операции со сроками.
- [ ] Нагрузка по сотрудникам (агрегация по исполнителям).

## 4. Рекомендуемый порядок разработки

| № | Пакет | Зачем раньше |
|---|--------|----------------|
| 1 | Блок 7 — доводка приёмки | Быстрый закрываемый объём, завязан на этапы |
| 2 | Блок 8 — Папка ИД | Ядро контроля комплектности, влияет на закрытие этапов |
| 3 | Блок 9 — уведомления + Telegram/email | Нужны для приёмки и для «запроса статуса» |
| 4 | Блок 11 — экран руководителя | Крупный UI, опирается на метрики и сроки |
| 5 | Блок 12 — выгрузки / печать | Добить до договорного объёма |
| 6 | Блок 10 — мобилка | Можно параллельно с 11 после стабилизации карточки этапа |
| 7 | Деплой, приёмка, обучение | Финал Этапа 2 |

Параллелить имеет смысл: **8 ∥ 9** после стабилизации данных; **10 ∥ 11** после готовности карточки этапа и уведомлений.

## 5. Критерии готовности Этапа 2

Этап 2 считается готовым к акту, когда:

1. По каждому из блоков **7–12** есть работающий сценарий у пользователей заказчика.  
2. Папка ИД показывает комплектность и предупреждает на герметичности / опрессовке.  
3. Уведомления приходят в системе и дублируются хотя бы в один внешний канал (Telegram или email) — оба по договору желательно закрыть.  
4. С телефона можно вести текущий этап (условия, ключевые действия, нештатка).  
5. Руководитель видит схему / метрики / может массово двигать сроки.  
6. Есть выгрузка и печать перечня этапов.  
7. Система развёрнута на стенде заказчика, проведено обучение, подписан акт.

## 6. Что остаётся «на третий этап» / после договора

**В договоре третьего этапа нет.** Ниже — бэклог после сдачи Этапа 2.

### 6.1. Вне договора (только доп. соглашение)

Из пределов Приложения № 1:

- учёт материалов и инструмента;
- детализация по бригадам;
- табель рабочего времени;
- интеграции с внешними ИС / учётными системами;
- автоматическая подача заявок и обмен данными с контрагентами.

### 6.2. Из ТЗ — «после показа» / следующий шаг (не Этап 2 договора)

- отдельные интерфейсы ролей: планшет/телефон прораба, рабочие столы ПТО и офис-менеджера *(в Этапе 2 — адаптив и полевой UI; отдельные «кабинеты» ролей — после)*;
- отправка заявки на почту из системы, интеграция с почтой Timeweb;
- PDF заявки по фирменному бланку (нужен шаблон от заказчика);
- автоматическое подтверждение получения заявки адресатом.

### 6.3. Уточнения с заказчиком (могут попасть в Этап 2 или в доп.)

- нужен ли отдельный код роли «геодезист / специалист по договорам» в справочнике;
- канал уведомлений: оба (Telegram + email) сразу или поэтапно;
- точный список этапов, на которых жёстко блокировать закрытие при неполной папке ИД.

## 7. Зависимости от заказчика

- Доступы к серверу / домену для финального деплоя.  
- Telegram: решение (бот организации) и кто привязывает аккаунты.  
- Email: SMTP или сервис рассылки.  
- Список сотрудников и роли для обучения.  
- Подтверждение правил герметичности / опрессовки для папки ИД.  
- Шаблон бланка — только если PDF заявок берут в ближайший контур (иначе — после Этапа 2).
